# ACARS Hub v4.3 - Aircraft Session Architecture

This document describes the architecture decisions, data model, and implementation phases for
the v4.3 release. It is the authoritative reference for all agents working on v4.3 features.

## Version History of This Document

This document was originally written as the v4.2 plan. The work that actually shipped as
v4.2 (released as 4.2.x) was a different body of work: the remediation cycle, the message
ring buffer, timeseries compaction, and the migration 13-15 index/UUID cleanup. The aircraft
session architecture described here was never started, so the document has been renumbered
to **v4.3**.

Renumbering is not the only change. The document has been audited against the codebase at
version 4.2.2 and corrected in place. See Audit Corrections below for every claim that was
found to be stale, and Position Storage Design for the position-history rework that replaced
the original ADS-B polling design.

## Why v4.3 Exists

Prior to v4.3, the frontend carries the full cognitive burden of message processing: grouping
messages by aircraft, deduplicating, merging multi-part sequences, pairing ACARS messages to
ADS-B targets, and culling stale groups. This works but has fundamental limits:

- Historical context is lost on page load - the frontend only knows what arrived after connect
- ADS-B pairing is ephemeral - if an aircraft leaves and returns, prior messages are not linked
- Each connected client independently re-computes the same grouping logic
- There is no persistent record of where an aircraft was when it sent a message
- A new version of `@airframes/acars-decoder` silently leaves old messages undecoded

v4.3 moves all message intelligence to the backend and database, making the frontend a
stateful view of authoritative backend data rather than a computation engine.

## Position Storage Design

This section replaces the original "Position Smoothing" design. It is the largest change in
the renumbering, and it is driven by a hard constraint: ACARS Hub is deployed via adsb.im
onto hosts where database size is a real limit.

### Why the Original Design Was Replaced

The original plan called for the 5-second ADS-B poller to write smoothed positions for every
aircraft in range (30-second minimum interval, 500m/15-degree change threshold, 5-minute
cruise fallback). Three problems:

1. It stores positions for every aircraft on the chance that one later sends an ACARS
   message. Most never do.
2. It cannot recover position history from *before* the first ACARS message, which is exactly
   the context a user wants when a message arrives.
3. Measured cost is roughly 1 MB/day, ~368 MB/year at a moderately busy site.

readsb (the ADS-B source behind tar1090) already maintains per-aircraft position traces on
disk and serves them over HTTP. Fetching a trace when an aircraft becomes interesting is
strictly better than polling every aircraft continuously against the possibility.

### readsb Trace Endpoints

Availability is advertised in `/data/receiver.json`:

```json
{ "haveTraces": true, "json_trace_interval": 15.0, "version": "readsb 3.16.15" }
```

Paths, where `XX` is the **last two characters** of the lowercase ICAO hex:

```text
/data/traces/XX/trace_full_<hex>.json      cumulative trace for the current flight leg
/data/traces/XX/trace_recent_<hex>.json    trailing window, rewritten ~every 15s
```

Both are gzip-encoded. Directory listings are forbidden (403); individual files are fine.
`/globe_history/` is **not** available - there is no long-term archive to mine, only the live
trace set.

Response shape:

```json
{
  "icao": "a4f6a3", "r": "N419MA", "t": "E55P", "ownOp": "MAXAIR LLC",
  "timestamp": 1786471349.693,
  "trace": [[t_offset, lat, lon, alt_baro, gs, track, flags, baro_rate, ac_obj, type, alt_geom, ...]]
}
```

Each trace point is a **14-element array**. Field notes:

- `t_offset` is seconds relative to the file-level `timestamp`. Absolute time is
  `timestamp + t_offset`.
- `alt_baro` is feet, **or the string `"ground"`**. It must be parsed as
  `number | "ground"`, not as a number.
- `flags` is a bitfield. **bit0 = stale position** (set on the first point after a reception
  gap). **bit1 = new flight leg** - measured as `0` across all 2,348 sampled points, so it
  cannot be relied on for leg detection.
- `ac_obj` (index 8) is a full aircraft JSON object on roughly 25% of points and `null`
  otherwise. It accounts for ~42% of raw payload bytes and is discarded on ingest.

### Measured Behaviour

All figures below were measured against a live readsb 3.16.15 instance (154 aircraft, single
receiver, Albuquerque). Any agent re-verifying should expect similar shapes, not identical
numbers.

**Traces are not pre-thinned.** This is the finding that most shaped the design. Aggregate
point spacing is 5.0s median, but **35% of points are less than 2 seconds apart**. Locally
received aircraft cluster at 1.0-2.2s / ~250m spacing (one aircraft: 463 points in 32
minutes). Density does not decay with age - the oldest quartile of a trace is as dense as
the newest. Ingesting a trace verbatim is roughly **4x worse** than the original smoothing
rule. Thinning is mandatory; the trace only relocates where it happens.

**Traces survive the aircraft leaving coverage.** All 15 aircraft observed dropping out of
`aircraft.json` were still serving complete traces 30+ minutes later. Trace fetch is keyed
on hex alone and does **not** require presence in `aircraft.json`. This is the enabler for
fetch-on-ACARS-message.

**Traces bridge reception gaps.** One trace contained 10 distinct reception segments across
60.5 minutes, with gaps of 792s, 951s, and 349s preserved as long-`dt` jumps between
consecutive points. The largest gap observed anywhere was 799s / 198 km. So a returning
aircraft's trace contains the out-of-coverage period *and* everything before it.

**Conditional GET works.** Both `Last-Modified` and `ETag` return 304, and `HEAD` is
supported. Refresh cost collapses:

| Strategy                                | Requests | Wire bytes | Elapsed |
| --------------------------------------- | -------- | ---------- | ------- |
| Sequential full fetch, all 154 aircraft | 153      | 86 KiB     | 0.20s   |
| Conditional refresh (all unchanged)     | 54       | 1.3 KiB    | 0.05s   |
| Concurrent x8, full fetch               | 153      | 87 KiB     | 0.03s   |

**Coverage is ADS-B only.** 49/49 `adsb_icao` aircraft had traces. **98 of 103 `adsc`
(satellite) aircraft returned 404** - the 5 that had traces also had terrestrial ADS-B.
HFDL and ADS-C sessions get nothing from this mechanism and must degrade gracefully.

**Douglas-Peucker thinning is highly effective.** At 100m tolerance, 1,145 points reduce to
103 (**11x**, worst case 29% retained). 100m is well below map render resolution at any
practical zoom.

### Flight Leg Boundaries and Ground Behaviour

This is the critical finding for the finalizer, and it resolves the turnaround scenario
directly: aircraft lands at a nearby airport, sits for an hour, departs again as a different
flight.

**readsb resets `trace_full` at the ground-to-airborne transition.** Four departures were
caught mid-climb with ground points still in their traces. In every case the trace **began on
the ground with no prior arrival leg**:

| Hex      | Flight  | readsb `messages` | Trace span | First point | Transitions in trace |
| -------- | ------- | ----------------- | ---------- | ----------- | -------------------- |
| `a2cfa2` | SKW3970 | 7,999             | 20.2 min   | `ground`    | 1 x LIFTOFF          |
| `a7d267` | LN603AC | 4,406             | 4.3 min    | `ground`    | 1 x LIFTOFF          |
| `a3e503` | ENY3901 | 4,037             | 4.1 min    | `ground`    | 1 x LIFTOFF          |
| `aa2a7f` | SKW4897 | 3,670             | 8.0 min    | `ground`    | 1 x LIFTOFF          |

The `messages` counter accumulates for as long as readsb has tracked the hex. 7,999 messages
against a 20.2-minute trace span is only explicable as a trace reset. No trace contained a
TOUCHDOWN followed by a LIFTOFF.

The departure trace for `a2cfa2` shows the ground phase in full - taxi at 2-9 kt with two
reception gaps (252s, 135s) while on the ground behind terrain, then liftoff:

```text
 idx    t_off      alt      gs  flag       dt  note
   0      0.0   ground     2.2     1      0.0  GROUND
   2    272.1   ground     9.2     1    252.2  GROUND <<GAP 252s>>
  11    462.0   ground     8.2     1    135.0  GROUND <<GAP 135s>>
  16    484.6   ground     5.2     0      5.0  GROUND
  17    497.6     5100     5.2     0     13.1  *** LIFTOFF ***
  18    541.3     5150    None     1     43.7
```

**Answer to the turnaround question**: for the common case, readsb has already done the
segmentation. The inbound flight's trace is gone by the time the outbound flight is airborne,
so a trace fetched during the departure contains only the departure (plus its taxi-out).

**But this must not be relied on as the only defence**, for three reasons:

1. The reset is a readsb implementation detail, unversioned and unadvertised. It could change.
2. `flags` bit1 (new leg) is `0` at this station, so there is no in-band marker to confirm a
   reset happened.
3. A **fetch timed between touchdown and liftoff** will legitimately return the arrival leg.
   If an ACARS message arrives while the aircraft is parked - gate messages are common - the
   fetch returns the *inbound* trace. That is correct data for the inbound session and wrong
   data for a subsequent outbound one.

So yes, to answer the question directly: **the finalizer and the refresher must both be
session-aware and must clip by absolute timestamp.** The rule is below.

### Trace-to-Session Attribution Rule

Every ingested trace point is clipped against the session before storage. This is not
optional and it is the single most important correctness rule in the position pipeline.

```text
Given session S (first_seen, last_seen) and a fetched trace T:

1. Convert every point to absolute time: abs_t = T.timestamp + point[0]
2. Discard any point where abs_t < (S.first_seen - PRE_ROLL)
3. Discard any point where abs_t > (S.last_seen + POST_ROLL)
4. Discard any point whose lat or lon is null
5. Split the remainder on any dt > LEG_SPLIT_GAP; if more than one segment
   survives AND the segments are separated by a ground phase, keep only the
   segment overlapping [S.first_seen, S.last_seen] and log a warning
6. Thin the survivors (Douglas-Peucker, 100m) and store
```

`PRE_ROLL` is the deliberate "free history" window - the whole point of the trace approach is
getting positions from before first contact. 15 minutes for `adsb` sessions. `POST_ROLL` is
small (60s) and only exists to catch clock skew between readsb and the container.

Step 5 is the turnaround guard. A trace that spans a ground phase and contains points both
well before and well after it belongs to two flights, whatever readsb did.

`alt_baro == "ground"` points are retained, not discarded - taxi trails are useful and the
ground phase is what identifies a leg boundary in the first place. They must not be fed to
altitude-based logic as if `"ground"` were `0`.

### Position Schema

Row cost was measured by building real SQLite files (200,000 rows, VACUUMed):

| Schema                                                                       | Bytes/position |
| ---------------------------------------------------------------------------- | -------------- |
| Original v4.2 shape (AUTOINCREMENT rowid + `UNIQUE` + redundant index)       | 86.5           |
| `WITHOUT ROWID`, `PRIMARY KEY(session_id, timestamp)`, REAL lat/lon          | 50.5           |
| `WITHOUT ROWID` + scaled integers                                            | **29.7**       |
| Delta-varint + zlib blob, one row per session                                | 12-16          |

The original shape is **2.9x** larger than a tuned row layout, because it declares both
`UNIQUE(session_id, timestamp)` and a separate `CREATE INDEX` on the same two columns - the
same duplicate-B-tree waste that `DB_OPTIMIZATION.md` flags on `rrd_import_registry`.

The blob layout is another ~2x better and gets *more* efficient with density (58% saving at
37 points/session, 62% at 60). It matches the access pattern exactly, since positions are
always read as a whole session for `GET /api/aircraft/:sessionId/history`, and it makes
retention a single-row delete. It is rejected for now because it forecloses SQL-queryable
positions, which kills the coverage-heatmap idea and any future spatial query. **Revisit if
measured growth exceeds projections.**

Adopted schema (migration 16):

```sql
CREATE TABLE aircraft_positions (
    session_id  INTEGER NOT NULL REFERENCES aircraft(id) ON DELETE CASCADE,
    timestamp   INTEGER NOT NULL,   -- Unix seconds (not ms; positions are never sub-second)
    lat_e5      INTEGER NOT NULL,   -- degrees * 1e5  (~1.1 m resolution)
    lon_e5      INTEGER NOT NULL,   -- degrees * 1e5
    alt_25      INTEGER,            -- feet / 25, NULL when unknown, -1 sentinel for "ground"
    track_deg   INTEGER,            -- degrees true, 0-359
    speed_kt    INTEGER,            -- knots ground speed
    PRIMARY KEY (session_id, timestamp)
) WITHOUT ROWID;
```

No secondary index. The primary key is the access path and `WITHOUT ROWID` means it is the
table. Do not add `idx_positions_session_time` - it would duplicate the PK.

`lat_e5`/`lon_e5` at 1.1m resolution is far finer than ADS-B position accuracy. `alt_25`
matches the 25-foot quantisation the source already uses. The `-1` ground sentinel keeps the
column integer-typed; readers must translate it back.

### Projected Growth

At ~250 ACARS-active aircraft/day with trace-sourced, DP-thinned positions (~10
points/session at 29.7 B):

| Scenario                                        | rows/day | MB/day | MB/30d | MB/year |
| ----------------------------------------------- | -------- | ------ | ------ | ------- |
| ACARS-gated + DP@100m (adopted)                 | 2,500    | 0.12   | 3.6    | 44      |
| ACARS-gated + DP@100m, busy site (800 aircraft) | 8,000    | 0.38   | 11.5   | 140     |
| ACARS-gated, raw trace (no thinning)            | 9,250    | 0.44   | 13.3   | 162     |
| Original v4.2 design (all aircraft, polled)     | 21,000   | 1.01   | 30.2   | 368     |

For scale: `timeseries_stats` already sits at roughly 63 MB steady-state under its 1,095-day
default retention. The adopted design is a fraction of an existing accepted cost.

### Retention Feature Flag

`ENABLE_POSITION_HISTORY`, default **on**, parsed with the existing `isEnabled()` helper
(`config.ts:151`) and surfaced through `features_enabled` like `ENABLE_ADSB`.

Because positions are fetched on demand rather than accumulated, the flag does **not** gate
availability - only persistence. With the flag off:

- Active sessions still get full trails, served from the in-memory warm cache
- Trails survive in cache for a cooldown period after the session ends
- Nothing is written to `aircraft_positions`; the table stays empty
- Historical drill-down from search returns no trail for ended sessions

That is a materially better flag-off story than the original polling design could offer:
degraded to "no history for departed aircraft", not "no trails at all".

**The flag must not gate the migration.** There is no precedent for config-conditional
migrations in this codebase - `MigrationStep.upgrade` receives only a `Database` handle
(`db/migrations/types.ts:7-11`), no migration reads `process.env`, and `runMigrations()`
throws unrecoverably on an unrecognised schema state (`db/migrate.ts:256-261`). A flag flip
after the migration ran would produce exactly that state. Create the table unconditionally;
gate the **writes**. This matches how `DB_SAVE_DAYS` and `TIMESERIES_RETENTION_DAYS` already
work.

The flag is specced from the start on the understanding that it may be removed if measured
cost stays negligible. Keep it cheap: a single write-path guard plus a prune-path guard.

### `aircraft` - Flight Session Registry

Each row represents one flight session. Two appearances of the same aircraft are two rows.
This is intentional - see Session Lifecycle below.

```sql
CREATE TABLE aircraft (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    icao_hex       TEXT,                      -- ICAO 24-bit address (uppercase hex, e.g. "ABC123")
    callsign       TEXT,                      -- Flight number / callsign (e.g. "UAL123")
    tail           TEXT,                      -- Registration (e.g. "N12345")
    first_seen     INTEGER NOT NULL,          -- Unix seconds
    last_seen      INTEGER NOT NULL,          -- Unix seconds; updated on every contact
    is_active      INTEGER NOT NULL DEFAULT 1,-- 1 = session alive, 0 = timed out
    session_type   TEXT    NOT NULL DEFAULT 'adsb',
    -- 'adsb' | 'vdlm2' | 'hfdl' | 'adsc' | 'acars_only'
    -- Controls timeout threshold. See Session Timeout Thresholds below.
    pairing_method TEXT,
    -- 'hex' | 'callsign' | 'tail' | 'acars_only' - how the session was first established
    trace_state    TEXT    NOT NULL DEFAULT 'none'
    -- 'none' | 'pending' | 'live' | 'final' | 'unavailable' - see Trace Fetch Lifecycle
);

CREATE INDEX ix_aircraft_active_hex  ON aircraft(is_active, icao_hex);
CREATE INDEX ix_aircraft_last_seen   ON aircraft(last_seen);
```

**Only two indexes.** The original plan specified five single-column indexes
(`icao_hex`, `callsign`, `tail`, `is_active`, `last_seen`). The session matching query filters
`is_active = 1` and then matches on identifiers, so a composite `(is_active, icao_hex)` serves
the hot path; `last_seen` serves the expiry sweep. Callsign and tail lookups fall back to a
scan of the active set, which is tens of rows, not millions. Adding indexes for them repeats
the exact mistake migrations 13 and 15 were written to undo. Verify with
`EXPLAIN QUERY PLAN` before adding any third index.

### Session Identifier Type

The original plan used a `session_id TEXT` UUID as the FK target. **This is rejected.**
Migration 14 removed UUIDs from this schema for measured size reasons (~838 MB projected at
11M rows). Re-introducing a 36-character text key as an FK target would undo that work.

Sessions use the integer `aircraft.id`. Consequently:

- `messages.aircraft_id` (`text(36)`, nullable, dead, never written) is **not** reused.
  Migration 16 adds `messages.session_id INTEGER` alongside it and leaves the dead column
  for a later cleanup migration to drop, keeping migration 16 free of a table rebuild.
- The index question raised by `DB_OPTIMIZATION.md` is resolved: `ix_messages_aircraft_id`
  stays dropped forever. Phase 6 creates `ix_messages_session_id` on the new integer column
  once it is actually populated.

### `decoded_messages` - Decoded Text Storage

Stores the output of `@airframes/acars-decoder` per message, along with the decoder version
that produced it. This enables version-aware re-processing. See Decoder Re-processing below.

```sql
CREATE TABLE decoded_messages (
    message_id      INTEGER PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
    decoder_version TEXT    NOT NULL,
    decode_level    TEXT    NOT NULL CHECK(decode_level IN ('full', 'partial', 'none')),
    decoder_name    TEXT,
    decoded_json    TEXT,   -- NULL when decode_level = 'none'
    decoded_at      INTEGER NOT NULL
) WITHOUT ROWID;

CREATE INDEX ix_decoded_version_level ON decoded_messages(decoder_version, decode_level);
```

Keyed on `messages.id`, not a UUID, for the same reason as sessions. The relationship is 1:1,
so `message_id` is the primary key directly - no surrogate `id`, no separate unique index.

One composite index replaces the plan's two single-column indexes. The reprocessor's query is
always "rows for a version other than the installed one, in decode-level priority order",
which `(decoder_version, decode_level)` serves; neither column is independently selective
enough to justify its own B-tree.

Rows with `decode_level = 'none'` are stored intentionally. Without them, there is no way
to distinguish "never tried" from "tried and could not decode" during re-processing sweeps.

**Growth note**: this table is 1:1 with `messages`, which has a 7-day default retention, so
it inherits that bound via `ON DELETE CASCADE`. But `decoded_json` is unbounded text and will
be a material fraction of DB size. Store only what the frontend renders - do not persist the
decoder's full internal output verbatim without measuring it first.

General-purpose configuration table for values that must survive restarts and are not

```sql
CREATE TABLE system_config (

```

## Session Lifecycle

### Session Types and Timeout Thresholds

A session is considered the "same flight" as long as a contact arrives within the timeout
window. After the timeout, any new contact creates a new session row, even if `icao_hex`,
`callsign`, and `tail` are identical.

| `session_type` | Timeout    | Rationale                                                |
| -------------- | ---------- | -------------------------------------------------------- |
| `adsb`         | 20 minutes | Local Mode S; aircraft lands or leaves range quickly     |
| `vdlm2`        | 45 minutes | Slightly longer range; taxi and gate messages common     |
| `hfdl`         | 6 hours    | Oceanic; multi-hour gaps between position reports normal |
| `adsc`         | 12 hours   | Polar/oceanic; very long gaps by design                  |
| `acars_only`   | 90 minutes | No position data; conservative to avoid false splits     |

The `session_type` is set to the most authoritative source that has contributed to the session.
Priority: `adsb` > `vdlm2` > `hfdl` > `adsc` > `acars_only`. If an `acars_only` session
later receives ADS-B data, `session_type` is upgraded and `pairing_method` is updated.

**These timeouts govern session identity only. They must not be used as trace-fetch
deadlines** - see Trace Fetch Lifecycle. Trace availability is a property of readsb, not of
this application's session model, and the `hfdl` (6h) and `adsc` (12h) windows are far beyond
any observed trace lifetime.

### Session Matching Algorithm

On every inbound message or ADS-B position, the session service runs:

```text
1. Query active sessions (is_active = 1) matching any of: icao_hex, callsign, tail
2. For each candidate, compute elapsed = now - last_seen
3. If elapsed < TIMEOUT[session_type]:
     -> Update last_seen, enrich identifiers if new data, return session id
4. If no live match:
     -> Create new session, set session_type from message source
     -> Return new session id
```

Matching priority is `icao_hex` > `callsign` > `tail`. If a session is found by callsign
but the incoming data includes a new `icao_hex` not yet on that session, update the session
row with the hex. This is "session enrichment" - identifiers accumulate over a session's life.

### Session Expiry

A background task (extending the existing scheduler in `services/background-services.ts`)
runs every 5 minutes and marks sessions inactive:

```sql
UPDATE aircraft SET is_active = 0
WHERE is_active = 1
  AND last_seen < (now - TIMEOUT[session_type])
```

Inactive sessions are retained in the database for historical queries. They are never deleted
by the expiry process.

**Retention**: sessions and their positions are pruned by the existing `pruneDatabase()`
schedule, not by expiry. A session whose messages have all aged out of the 7-day window has
no reason to persist. This must be added to `prune.ts` in Phase 6 - a session table that
grows forever would defeat the point of this document.

### Callsign Reuse Edge Case

Airlines reuse flight numbers daily. `UAL123` on Monday is a different aircraft than `UAL123`
on Tuesday. The timeout logic handles routine cases, but a defensive check applies when:

- A session exists with a matching callsign
- Elapsed time is > 80% of the session's timeout threshold
- The session has no `icao_hex` (callsign-only match)

In this case, treat the incoming contact as a new session. Log a warning. This avoids
erroneously extending a stale callsign-only session.

## Trace Fetch Lifecycle

Three mechanisms, all driven by `services/trace-fetcher.ts`. Each is independently testable
and each has a distinct trigger.

`aircraft.trace_state` tracks progress: `none` -> `pending` -> `live` -> `final`, or
`unavailable` when readsb has no trace for the hex.

### Preconditions

- `/data/receiver.json` reports `haveTraces: true`, checked once at startup and cached. If
  false, the whole subsystem is inert and `trace_state` stays `none`.
- The session has a known `icao_hex`. Traces are keyed on hex only; a callsign-only or
  tail-only session cannot be fetched for until enrichment supplies a hex.
- A 404 is a **normal outcome**, not an error. Satellite-only aircraft (`adsc`) will 404
  almost always. Log at debug, set `trace_state = 'unavailable'`, do not retry aggressively.

### Trigger 1 - On First ACARS Pairing

When a session first acquires an ACARS message and has a hex, fetch `trace_full` immediately.
This is the high-value path: it retrieves position history from *before* the message arrived,
at no storage cost for aircraft that never send one.

### Trigger 2 - Periodic Refresh of Active Sessions

A scheduler task refreshes traces for active, ACARS-paired sessions.

- Interval: **60 seconds** minimum. readsb rewrites trace files every
  `json_trace_interval` (15s), so polling faster is pure waste.
- Use `If-Modified-Since` (or `If-None-Match`) from the stored validator. Unchanged files
  cost a 304 and near-zero bytes.
- **Batch with a concurrency cap of 4-8.** Measured throughput is ~1 ms/request against a
  local readsb, but a remote or shared tar1090 deserves politeness. Do not fan out to all
  sessions at once.
- Only ACARS-paired sessions are refreshed. This is typically 5-20 aircraft, not 150.
- Refreshed points are clipped by the Trace-to-Session Attribution Rule and upserted on
  `(session_id, timestamp)`, so overlap between `full` and `recent` is idempotent. Observed
  overlap is 100-270s.

### Trigger 3 - Finalizer on Dropout

The finalizer captures the definitive trace once an aircraft stops being seen.

**Trigger on dropout detection, not session expiry.** An aircraft is considered dropped when
absent from `aircraft.json` for two consecutive poll cycles. Session expiry is a fallback in
case dropout was missed.

The deadline is independent of `session_type`:

- Capture within **10 minutes** of last contact. Trace persistence was verified at 30+ minutes
  but the upper bound is unknown, so the deadline is deliberately conservative.
- Never derive the deadline from the session timeout table. A 12-hour `adsc` timeout would
  guarantee a 404.

On success: apply the attribution rule, thin, store, set `trace_state = 'final'`. A finalized
session is never refreshed again.

### Returning Aircraft

If an aircraft returns and matches an existing active session, refresh resumes and the newly
fetched trace supplies the coverage gap plus the earlier positions. Upsert on
`(session_id, timestamp)` makes re-ingesting the overlapping portion a no-op.

If it returns *after* the session expired, it is a new session by definition. The new session
fetches its own trace and clips it to its own `first_seen`, so the previous flight's positions
are discarded by step 2 of the attribution rule even if readsb still has them.

### Warm Cache

Trace points for active sessions are held in memory alongside the existing message ring
buffer (`services/message-ring-buffer.ts`), so the frontend never waits on a DB read for a
live aircraft's trail. This cache is what makes `ENABLE_POSITION_HISTORY=false` tolerable:
active sessions keep full functionality, plus a cooldown window after the session ends.

## Retroactive Pairing

When a new ADS-B target appears, the backend checks for historical ACARS messages that
should belong to this session but arrived before the ADS-B signal was first received.

```text
1. New ADS-B contact creates or updates a session (session id S, hex H, callsign C, tail T)
2. Query: SELECT id FROM messages
          WHERE session_id IS NULL
            AND msg_time > (first_seen - LOOKBACK_WINDOW)
            AND (icao = H OR flight = C OR tail = T)
3. For each match: UPDATE messages SET session_id = S WHERE id = ?
4. Emit session_paired event with [session id, [ids]]
```

`LOOKBACK_WINDOW` is 60 minutes for `adsb` sessions. For `hfdl`/`adsc` sessions the window
scales with the session timeout.

Retroactive pairing is also run on session enrichment - when a new identifier (e.g. `icao_hex`)
is added to an existing session, the query runs again with the newly available identifier.

**Query cost warning**: this query has no supporting index. `messages` has only
`ix_messages_icao`, `ix_messages_msgno`, and `ix_messages_type_time` after migration 15;
`flight` and `tail` indexes were deliberately dropped. Run `EXPLAIN QUERY PLAN` during
implementation. If it degrades, prefer narrowing the time window over adding indexes back -
those indexes were removed for measured size reasons and cost ~154 MB at 11M rows.

## Decoded Message Storage and Re-processing

### At Ingest Time

When a new ACARS message arrives and is stored, the backend:

1. Calls `@airframes/acars-decoder` with the message text and label
2. Writes one row to `decoded_messages` (with `decode_level = 'none'` if undecoded)
3. Sets `decoded_at` and `decoder_version` from the installed package version
4. The `decodedText` field on the outbound socket message is populated from this row

The `enrichMessage()` function in `formatters/enrichment.ts` is the correct integration point.
It already calls the decoder inline (`enrichment.ts:176`) but **does not persist the result** -
every retrieval path re-decodes. Post-v4.3 it writes to `decoded_messages` and subsequent
retrievals JOIN rather than re-decode.

The paths that currently re-decode, and therefore benefit:

| Path                    | Location                          | Cost                          |
| ----------------------- | --------------------------------- | ----------------------------- |
| Live ingest             | `background-services.ts:352`      | 1 per message (unavoidable)   |
| Ring buffer warm-up     | `message-ring-buffer.ts:348,375`  | up to 700 decodes at startup  |
| Search results          | `socket/handlers/search.ts:88`    | every query                   |
| Alert term search       | `socket/handlers/alerts.ts:292`   | every query                   |
| Alerts by term          | `socket/handlers/alerts.ts:337`   | every query                   |

### Version Detection at Startup

```typescript
// At startup, after DB is initialized
const installed = getInstalledDecoderVersion(); // from @airframes/acars-decoder/package.json
const stored = systemConfig.get("acars_decoder_installed_version");

if (installed !== stored) {
  logger.info("acars-decoder version change detected", { stored, installed });
  systemConfig.set("acars_decoder_installed_version", installed);
  decoderReprocessor.schedule();
}
```

A simple string equality check is sufficient. Semantic versioning comparison is unnecessary -
any version change (including a downgrade) warrants re-processing to ensure consistency.

### Background Reprocessor

The reprocessor is a low-priority background service added to the scheduler. It must not
starve the event loop while 100k+ messages are being re-processed.

**Processing order** (most likely to benefit from a new decoder version first):

1. Messages with no row in `decoded_messages` (legacy data, never processed)
2. Messages where `decode_level = 'none'` and `decoder_version != installed`
3. Messages where `decode_level = 'partial'` and `decoder_version != installed`
4. Messages where `decode_level = 'full'` and `decoder_version != installed`

**Execution model**:

- Batch size: 250 messages per iteration
- Yield between batches: `await new Promise(resolve => setImmediate(resolve))`
- Persist cursor to `system_config.acars_decoder_reprocess_cursor` after each batch
- On restart, read cursor and resume from that `messages.id`
- On completion, set `acars_decoder_reprocess_status = 'completed'`

**When a decode changes**:

If re-processing produces a different `decode_level` or `decoded_json` from what is stored,
the reprocessor updates the row and emits a `message_decode_updated` Socket.IO event:

```typescript
// Server -> client
socket.emit("message_decode_updated", {
  id: number;
  decodedText: DecodedText | null;
});
```

Clients update any matching message currently in their view. This lets users watching Live
Messages see decodes improve in real time as the reprocessor runs.

## Backend Processing Pipeline Changes

### What Moves from Frontend to Backend

| Concern                                  | Current location                          | v4.3 location                                   |
| ---------------------------------------- | ----------------------------------------- | ----------------------------------------------- |
| `@airframes/acars-decoder` text decoding | Backend (`enrichment.ts:176`) - done      | Backend (now persisted to DB)                   |
| Alert term matching                      | Backend (`insert.ts:244-399`) - done      | Unchanged                                       |
| Duplicate detection (3 strategies)       | Frontend (`messagesSlice.ts:280-462`)     | Backend (at ingest, before DB write)            |
| Multi-part merging (AzzA, AAAz)          | Frontend (`messageDecoder.ts:125-321`)    | Backend (accumulate parts, write merged)        |
| Message grouping by identifier           | Frontend (`messagesSlice.ts:208-278`)     | Backend (replaced by session service)           |
| ADS-B / ACARS pairing                    | Frontend (3 separate implementations)     | Backend (session service + retroactive pairing) |
| Culling decisions                        | Frontend (`messageCulling.ts:108-167`)    | Backend (controls what is sent per client)      |

The frontend becomes a **render target**: it receives pre-processed, pre-grouped,
pre-decoded data and renders it. It performs no business logic on messages.

Note the three independent ADS-B pairing implementations that Phase 10 must collapse:
`utils/aircraftPairing.ts:128-162`, `utils/messageCulling.ts:32-91`, and
`components/MessageGroup.tsx:89-111`.

### New Ingest Pipeline

```text
TCP message arrives
  -> MessageQueue.push()
  -> Dedup check (3 strategies, against recent messages)
      -> Duplicate: increment counter, do not insert new row
      -> Multi-part: accumulate in memory, merge when complete, then continue
  -> DB insert (messages table)
  -> Session matching (find or create aircraft session, set session_id)
  -> enrichMessage() - field normalization, airline lookup, ground station lookup
  -> decoded_messages write (decoder output + version)
  -> Alert term matching -> alert_matches write if matched
  -> Trace fetch trigger if first pairing for this session
  -> Broadcast session_messages_updated to all clients
```

Dedup at ingest is a **behaviour change with a data consequence**: duplicate receptions are
currently each persisted as a separate `messages` row. Suppressing them reduces DB growth,
but the "duplicates" counter the frontend currently derives must be persisted instead, or
that information is lost. Decide explicitly in Phase 8.

### New Server to Client Events

```typescript
// Full session object: sent on connect and when session state changes significantly
"aircraft_session": {
  sessionId: number;
  icaoHex: string | null;
  callsign: string | null;
  tail: string | null;
```


```text
  -> Returns: all sessions (active and historical) matching identifiers
```

### LiveFilters Type

```typescript
interface LiveFilters {
  decoderTypes?: string[]; // ['acars', 'vdlm2', 'hfdl', ...]
  labelsOnly?: string[]; // Only messages with these labels
  alertsOnly?: boolean;
  hasTextOnly?: boolean;
  adsbPairedOnly?: boolean; // Only sessions with ADS-B data

```

When a client emits `set_live_filters`, the backend marks all sessions matching the old
filter as "unsubscribed" for that client and sends a fresh `initial_state` for the new filter.
The frontend clears its session map and re-populates from `initial_state`.

## Frontend Changes

### What the Frontend No Longer Does

- No message grouping logic (`messagesSlice.ts:208-278` gutted)
- No duplicate detection (`messagesSlice.ts:280-462`, `services/messageDecoder.ts:75-116`)
- No multi-part merging (`services/messageDecoder.ts:125-321`)
- No ADS-B/ACARS pairing (all three implementations removed)
- No culling (`utils/messageCulling.ts` deleted)

The frontend already does no decoding and no alert matching - those are backend-only today.

### New AppStore Shape

```typescript
// Replaces MessageGroup-based structure
interface AppStore {
  sessions: Map<number, AircraftSession>; // keyed by session id
  adsbPositions: Map<string, Aircraft>; // keyed by icao_hex (live map positions)
  filters: LiveFilters;
  connectionState: "connected" | "disconnected" | "reconnecting";
  // ... alerts, terms, status unchanged
}
```

### State-Based Filtering

Filter changes follow this flow:

1. User changes a filter in the UI
2. Frontend emits `set_live_filters` with new filters
3. Frontend clears its sessions map immediately (shows loading state)
4. Backend sends `initial_state` with sessions matching the new filter
5. Frontend populates sessions map from `initial_state`
6. Backend continues sending incremental updates (`session_messages_updated`, etc.)

This eliminates client-side filter logic entirely. The frontend never needs to decide which
messages to show or hide - the backend sends only what matches the current filter.

## Architecture Invariants

These rules must be preserved throughout v4.3 implementation:

1. **The backend is the source of truth.** The frontend renders; it does not compute.
2. **Sessions are immutable once created.** A new flight is always a new row, even for the
   same aircraft. Historical data must not be retroactively re-assigned to different sessions.
3. **Every trace point is clipped to its session before storage.** Never trust a trace file
   to contain exactly one flight leg. See the Trace-to-Session Attribution Rule.
4. **Trace availability is never assumed.** 404 is a normal outcome. `haveTraces: false`,
   satellite-only aircraft, and non-readsb sources must all degrade to no-trail, not error.
5. **No index may duplicate a primary key or another index.** Migrations 13 and 15 exist to
   undo exactly that mistake. Justify every new index with `EXPLAIN QUERY PLAN`.
6. **Integer keys only.** No UUID or text surrogate keys in new schema. Migration 14 removed
   them for measured size reasons.
7. **Cascade deletes are the only pruning mechanism for `decoded_messages`.** Never delete
   from it directly. Delete from `messages` and let the cascade handle it.
8. **Every new table has a retention story before it ships.** An unbounded table is a bug.
9. **The decoder reprocessor is non-blocking.** It must yield between batches. A slow
   re-process must never delay message ingestion or socket broadcasts.
10. **All new services follow the singleton pattern** used by `MessageQueue`, `AdsbPoller`,
    etc. Export a `getXxx()` factory and a `destroyXxx()` for test cleanup.
11. **Every phase ships with tests.** See `TESTING.md` and the Testing Mandate in `AGENTS.md`.

## Open Questions

Unresolved items that need answering during implementation. None blocks Phase 1.

1. **Upper bound on readsb trace TTL.** Verified at 30+ minutes; the real limit is unknown.
   Affects the finalizer deadline. Requires a multi-hour observation run.
2. **Does `trace_full` have a point cap?** A long flight may silently lose its oldest history.
   The largest observed was 463 points over 32 minutes.
3. **Is the ground-to-airborne trace reset stable across readsb versions?** Observed on
   3.16.15. The attribution rule does not depend on it, but the refresh interval could be
   relaxed if it were guaranteed.
4. **Non-readsb ADS-B sources.** `ADSB_URL` is user-configurable and may point at dump1090 or
   another aggregator with no trace endpoint. Capability detection handles it, but the
   resulting UX difference should be surfaced.
5. **Duplicate counter persistence** once ingest-time dedup lands (Phase 10).
6. **Does `features_enabled` grow or get a sibling event?** It is typed as `Decoders`
   (`acarshub-types/src/system.ts:127-141`) and already carries non-decoder fields. Adding
   `ENABLE_POSITION_HISTORY` to it is precedented but semantically wrong.
