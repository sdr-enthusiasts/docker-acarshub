# ACARS Hub v4.3 - Aircraft Session Architecture

This document describes the architecture decisions, data model, and implementation phases for
the v4.3 release. It is the authoritative reference for all agents working on v4.3 features.

## Version History of This Document

This document was originally written as the v4.2 plan. The work that actually shipped as
v4.2 (released as 4.2.x) was a different body of work: the remediation cycle, the message
ring buffer, timeseries compaction, and the migration 13-15 index/UUID cleanup. The aircraft
session architecture described here was never started, so the document has been renumbered
to **v4.3**.

Renumbering is not the only change. The document has been audited against the codebase at
version 4.2.2 and corrected in place. See Audit Corrections below for every claim that was
found to be stale, and Position Storage Design for the position-history rework that replaced
the original ADS-B polling design.

## Why v4.3 Exists

Prior to v4.3, the frontend carries the full cognitive burden of message processing: grouping
messages by aircraft, deduplicating, merging multi-part sequences, pairing ACARS messages to
ADS-B targets, and culling stale groups. This works but has fundamental limits:

- Historical context is lost on page load - the frontend only knows what arrived after connect
- ADS-B pairing is ephemeral - if an aircraft leaves and returns, prior messages are not linked
- Each connected client independently re-computes the same grouping logic
- There is no persistent record of where an aircraft was when it sent a message
- A new version of `@airframes/acars-decoder` silently leaves old messages undecoded

v4.3 moves all message intelligence to the backend and database, making the frontend a
stateful view of authoritative backend data rather than a computation engine.

## Storage Discipline

**Read this before designing anything in v4.3. It governs every other section.**

ACARS Hub is deployed via adsb.im onto hosts where storage is a real, hard constraint. For
those users database size is not a tuning detail, it is whether the application is usable at
all. **Minimising storage cost is an imperative, and it outranks feature completeness.** A
feature that cannot be built within a defensible storage budget is a feature that does not
ship in that form.

v4.3 is a net storage *increase*. That is accepted. It must be paid for deliberately,
measured, and justified — not absorbed silently.

### The Budget, and Why to Distrust It

The projections in Projected Growth range from ~44 MB/year for the adopted ACARS-gated design
to ~360 MB/year for a naive all-aircraft design retaining a year of data. **Both of those
numbers are within scope and acceptable.** Storage cost at that scale is not the concern.

The concern is that those numbers are extrapolations from one station over short observation
windows, and **the real figure is expected to land materially higher — plausibly an order of
magnitude above projection.** Treat every projection in this document as a hypothesis awaiting
falsification, not a budget already secured.

This has a concrete consequence for implementation:

- Measure **actual on-disk bytes** for `aircraft_positions` before Phase 8 is considered
  complete, and again after a week of real running.
- If actual growth exceeds projection by more than 2x, **stop and reassess** rather than
  continuing and hoping retention absorbs it.
- Record the measured figure in the PR. A projection that is never checked against reality is
  worthless.

### No Index Without Evidence

**Do not create an index for the sake of an index.** Every index must buy something specific,
traceable, and demonstrable.

The bar: a proposed index requires `EXPLAIN QUERY PLAN` output showing the planner actually
selects it for a query that really exists in the codebase. Paste that output in the PR
description. "It seems like this column will be queried" is not evidence. Neither is
"searching by tail is a feature", if the query path in fact uses FTS or a leading-wildcard
`LIKE` that no B-tree can serve.

This is not hypothetical caution. Migrations 13 and 15 exist purely to delete indexes added on
intuition, and `agent-docs/DB_OPTIMIZATION.md` measures the damage at roughly **1,086 MB of
dead index at 11M rows**. An index that duplicates a primary key or another index is a bug,
not an inefficiency.

### Features Have a Storage Cost, and It Is Negotiable

If a feature would cause database growth that is disproportionate or significant relative to
current database sizes, **that is a discussion to raise, not an implementation detail to
absorb.**

Concrete trigger: any single feature projected to add more than ~10% to steady-state database
size, or to rival the `messages` table itself, must be surfaced before it is built. The
outcome of that discussion may legitimately be that the feature is descoped, gated behind a
flag defaulting off, or redesigned around a cheaper data source — as the position pipeline
itself already was.

Say so early. A feature reworked at design time is cheap; one reworked after a migration has
shipped to users is not, because this codebase's migration chain is append-only with no
down-migration.

### Optimisations Are Measured, Never Assumed

Storage optimisation in this area has a **poor track record of intuition being correct**. Two
assumptions have already been reversed by measurement while writing this plan:

1. The original `aircraft_positions` schema was **2.9x larger than necessary** (86.5 vs 29.7
   bytes/position), because it declared a `UNIQUE` constraint and a separate index on the same
   two columns — two B-trees doing one job.
2. zlib compression of position blobs, self-evidently a win, measured **net-negative** at the
   session sizes actually observed. Its framing overhead exceeded what it recovered. Shipped
   unmeasured, it would have silently made the database larger while looking like an
   optimisation.

Therefore: **no storage optimisation lands without before/after byte counts on realistic
data.** Build the throwaway measurement first. It is usually twenty minutes and it has already
changed two decisions here.

### The Plan Is Expected to Be Fluid

This document is a plan, not a contract. Phase boundaries are a guide.

If, partway through implementation, an obvious optimisation or a materially better approach
becomes apparent, **stopping to consider it is explicitly in scope and encouraged.** Do not
plough on with a design that has been overtaken by something learned along the way, and do not
quietly defer a discovered improvement to a "later" that never arrives.

Equally, do not silently rewrite the plan. Surface the finding, quantify it, and update this
document so the next agent inherits the reasoning rather than the conclusion alone. Every
correction so far has been recorded here rather than in a summary document, and that is the
pattern to continue.

## Position Storage Design

This section replaces the original "Position Smoothing" design. It is the largest change in
the renumbering, and it is driven by a hard constraint: ACARS Hub is deployed via adsb.im
onto hosts where database size is a real limit.

### Why the Original Design Was Replaced

The original plan called for the 5-second ADS-B poller to write smoothed positions for every
aircraft in range (30-second minimum interval, 500m/15-degree change threshold, 5-minute
cruise fallback). Three problems:

1. It stores positions for every aircraft on the chance that one later sends an ACARS
   message. Most never do.
2. It cannot recover position history from *before* the first ACARS message, which is exactly
   the context a user wants when a message arrives.
3. Measured cost is roughly 1 MB/day, ~368 MB/year at a moderately busy site.

readsb (the ADS-B source behind tar1090) already maintains per-aircraft position traces on
disk and serves them over HTTP. Fetching a trace when an aircraft becomes interesting is
strictly better than polling every aircraft continuously against the possibility.

### readsb Trace Endpoints

Availability is advertised in `/data/receiver.json`:

```json
{ "haveTraces": true, "json_trace_interval": 15.0, "version": "readsb 3.16.15" }
```

Paths, where `XX` is the **last two characters** of the lowercase ICAO hex:

```text
/data/traces/XX/trace_full_<hex>.json      cumulative trace for the current flight leg
/data/traces/XX/trace_recent_<hex>.json    trailing window, rewritten ~every 15s
```

Both are gzip-encoded. Directory listings are forbidden (403); individual files are fine.
`/globe_history/` is **not** available - there is no long-term archive to mine, only the live
trace set.

Response shape:

```json
{
  "icao": "a4f6a3", "r": "N419MA", "t": "E55P", "ownOp": "MAXAIR LLC",
  "timestamp": 1786471349.693,
  "trace": [[t_offset, lat, lon, alt_baro, gs, track, flags, baro_rate, ac_obj, type, alt_geom, ...]]
}
```

Each trace point is a **14-element array**. Field notes:

- `t_offset` is seconds relative to the file-level `timestamp`. Absolute time is
  `timestamp + t_offset`.
- `alt_baro` is feet, **or the string `"ground"`**. It must be parsed as
  `number | "ground"`, not as a number.
- `flags` is a bitfield. **bit0 = stale position** (set on the first point after a reception
  gap). **bit1 = new flight leg** - measured as `0` across all 2,348 sampled points, so it
  cannot be relied on for leg detection.
- `ac_obj` (index 8) is a full aircraft JSON object on roughly 25% of points and `null`
  otherwise. It accounts for ~42% of raw payload bytes and is discarded on ingest.

### Measured Behaviour

All figures below were measured against a live readsb 3.16.15 instance (154 aircraft, single
receiver, Albuquerque). Any agent re-verifying should expect similar shapes, not identical
numbers.

**Traces are not pre-thinned.** This is the finding that most shaped the design. Aggregate
point spacing is 5.0s median, but **35% of points are less than 2 seconds apart**. Locally
received aircraft cluster at 1.0-2.2s / ~250m spacing (one aircraft: 463 points in 32
minutes). Density does not decay with age - the oldest quartile of a trace is as dense as
the newest. Ingesting a trace verbatim is roughly **4x worse** than the original smoothing
rule. Thinning is mandatory; the trace only relocates where it happens.

**Traces survive the aircraft leaving coverage.** All 15 aircraft observed dropping out of
`aircraft.json` were still serving complete traces 30+ minutes later. Trace fetch is keyed
on hex alone and does **not** require presence in `aircraft.json`. This is the enabler for
fetch-on-ACARS-message.

**Traces bridge reception gaps.** One trace contained 10 distinct reception segments across
60.5 minutes, with gaps of 792s, 951s, and 349s preserved as long-`dt` jumps between
consecutive points. The largest gap observed anywhere was 799s / 198 km. So a returning
aircraft's trace contains the out-of-coverage period *and* everything before it.

**Conditional GET works.** Both `Last-Modified` and `ETag` return 304, and `HEAD` is
supported. Refresh cost collapses:

| Strategy                                | Requests | Wire bytes | Elapsed |
| --------------------------------------- | -------- | ---------- | ------- |
| Sequential full fetch, all 154 aircraft | 153      | 86 KiB     | 0.20s   |
| Conditional refresh (all unchanged)     | 54       | 1.3 KiB    | 0.05s   |
| Concurrent x8, full fetch               | 153      | 87 KiB     | 0.03s   |

**Coverage is ADS-B only.** 49/49 `adsb_icao` aircraft had traces. **98 of 103 `adsc`
(satellite) aircraft returned 404** - the 5 that had traces also had terrestrial ADS-B.
HFDL and ADS-C sessions get nothing from this mechanism and must degrade gracefully.

**Douglas-Peucker thinning is highly effective.** At 100m tolerance, 1,145 points reduce to
103 (**11x**, worst case 29% retained). 100m is well below map render resolution at any
practical zoom.

### Flight Leg Boundaries and Ground Behaviour

This is the critical finding for the finalizer, and it resolves the turnaround scenario
directly: aircraft lands at a nearby airport, sits for an hour, departs again as a different
flight.

**readsb does NOT reliably reset `trace_full` at a flight-leg boundary.** A single trace can
hold an arrival and a later departure as two distinct flights. This is measured, not
theorised — see The Counterexample below.

An earlier draft of this document concluded the opposite, from the four departures tabulated
next. That conclusion was wrong and the correction is preserved here because the wrong version
is the intuitive one and would otherwise be re-derived.

#### The Evidence That Looked Like a Reset

Four departures were caught mid-climb with ground points still in their traces. In every case
the trace **began on the ground with no prior arrival leg**:

| Hex      | Flight  | readsb `messages` | Trace span | First point | Transitions in trace |
| -------- | ------- | ----------------- | ---------- | ----------- | -------------------- |
| `a2cfa2` | SKW3970 | 7,999             | 20.2 min   | `ground`    | 1 x LIFTOFF          |
| `a7d267` | LN603AC | 4,406             | 4.3 min    | `ground`    | 1 x LIFTOFF          |
| `a3e503` | ENY3901 | 4,037             | 4.1 min    | `ground`    | 1 x LIFTOFF          |
| `aa2a7f` | SKW4897 | 3,670             | 8.0 min    | `ground`    | 1 x LIFTOFF          |

The `messages` counter accumulates for as long as readsb has tracked the hex. 7,999 messages
against a 20.2-minute trace span is only explicable as a trace reset, and none of these four
contained a TOUCHDOWN followed by a LIFTOFF. The error was generalising from four same-day
departures to "readsb always resets".

The departure trace for `a2cfa2` shows the ground phase in full - taxi at 2-9 kt with two
reception gaps (252s, 135s) while on the ground behind terrain, then liftoff:

```text
 idx    t_off      alt      gs  flag       dt  note
   0      0.0   ground     2.2     1      0.0  GROUND
   2    272.1   ground     9.2     1    252.2  GROUND <<GAP 252s>>
  11    462.0   ground     8.2     1    135.0  GROUND <<GAP 135s>>
  16    484.6   ground     5.2     0      5.0  GROUND
  17    497.6     5100     5.2     0     13.1  *** LIFTOFF ***
  18    541.3     5150    None     1     43.7
```

#### The Counterexample

Within 40 minutes, the trace study caught `aca3d1` (N913WN, Boeing 737, Southwest). Its
**single `trace_full` file** spanned 95 minutes and contained two separate flights:

```text
seg0-2: arrival, descending to touchdown            218 pts
   >>> GAP 4385s (73.1 min), moved 1.14 km <<<      parked on the surface
seg3:   departure, climbing 5250 -> 11275 ft         90 pts
```

This is exactly the scenario the reset was supposed to protect against: an aircraft lands,
sits for over an hour, departs as a different flight — and both legs arrive in one fetch.

The likely mechanism is that a trace resets when the aircraft **ages out of readsb's memory**,
not at the leg boundary. The four departures above had been gone long enough to be purged and
so got fresh traces. A 73-minute turnaround stays inside readsb's retention window, so the
trace carries straight across it. **Turnaround duration, not flight state, decides whether you
get one leg or two** — and short turnarounds are the common case at a busy field.

A preserved copy of this trace is the regression fixture for the attribution rule. readsb's
live traces rotate, so it is the only durable copy. See Phase 7.

#### Consequence

**The Trace-to-Session Attribution Rule is load-bearing, not defence in depth.** Without it, a
departure session silently ingests the previous flight's arrival positions, and the resulting
trail is wrong in a way that looks plausible on a map.

Three further reasons not to trust leg detection to the source:

1. The reset behaviour is a readsb implementation detail, unversioned and unadvertised.
2. `flags` bit1 (new leg) measured `0` across all 2,348 sampled points, so there is no in-band
   marker confirming a reset happened.
3. A **fetch timed between touchdown and liftoff** returns the arrival leg regardless. Gate
   messages are common, so an ACARS message from a parked aircraft triggers exactly this.

So, directly: **the finalizer and the refresher must both be session-aware and must clip by
absolute timestamp.** The rule is below.

### Trace-to-Session Attribution Rule

Every ingested trace point is clipped against the session before storage. This is not
optional and it is the single most important correctness rule in the position pipeline.

```text
Given session S (first_seen, last_seen) and a fetched trace T:

1. Convert every point to absolute time: abs_t = T.timestamp + point[0]
2. Discard any point where abs_t < (S.first_seen - PRE_ROLL)
3. Discard any point where abs_t > (S.last_seen + POST_ROLL)
4. Discard any point whose lat or lon is null
5. Split the remainder on any dt > LEG_SPLIT_GAP; if more than one segment
   survives AND the segments are separated by a ground phase, keep only the
   segment overlapping [S.first_seen, S.last_seen] and log a warning
6. Thin the survivors (Douglas-Peucker, 100m)
7. Encode and store (see Storage Encoding and Compression)
```

`PRE_ROLL` is the deliberate "free history" window - the whole point of the trace approach is
getting positions from before first contact. 15 minutes for `adsb` sessions. `POST_ROLL` is
small (60s) and only exists to catch clock skew between readsb and the container.

Step 5 is the turnaround guard. A trace that spans a ground phase and contains points both
well before and well after it belongs to two flights, whatever readsb did.

`alt_baro == "ground"` points are retained, not discarded - taxi trails are useful and the
ground phase is what identifies a leg boundary in the first place. They must not be fed to
altitude-based logic as if `"ground"` were `0`.

### Position Schema

Row cost was measured by building real SQLite files (200,000 rows, VACUUMed):

| Schema                                                                       | Bytes/position |
| ---------------------------------------------------------------------------- | -------------- |
| Original v4.2 shape (AUTOINCREMENT rowid + `UNIQUE` + redundant index)       | 86.5           |
| `WITHOUT ROWID`, `PRIMARY KEY(session_id, timestamp)`, REAL lat/lon          | 50.5           |
| `WITHOUT ROWID` + scaled integers                                            | **29.7**       |
| Delta-varint + zlib blob, one row per session                                | 12-16          |

The original shape is **2.9x** larger than a tuned row layout, because it declares both
`UNIQUE(session_id, timestamp)` and a separate `CREATE INDEX` on the same two columns - the
same duplicate-B-tree waste that `DB_OPTIMIZATION.md` flags on `rrd_import_registry`.

A packed per-session blob is roughly another 2x better again, but it is **not** adopted, and
the reasoning is more subtle than raw bytes. See Storage Encoding and Compression below for
the full measurement and decision, including the finding that zlib is counterproductive at
the session sizes actually observed.

Provisional schema (migration 17, Phase 8 — confirm against the study report first):

```sql
CREATE TABLE aircraft_positions (
    session_id  INTEGER NOT NULL REFERENCES aircraft(id) ON DELETE CASCADE,
    timestamp   INTEGER NOT NULL,   -- Unix seconds (not ms; positions are never sub-second)
    lat_e5      INTEGER NOT NULL,   -- degrees * 1e5  (~1.1 m resolution)
    lon_e5      INTEGER NOT NULL,   -- degrees * 1e5
    alt_25      INTEGER,            -- feet / 25, NULL when unknown, -1 sentinel for "ground"
    track_deg   INTEGER,            -- degrees true, 0-359
    speed_kt    INTEGER,            -- knots ground speed
    PRIMARY KEY (session_id, timestamp)
) WITHOUT ROWID;
```

No secondary index. The primary key is the access path and `WITHOUT ROWID` means it is the
table. Do not add `idx_positions_session_time` - it would duplicate the PK.

`lat_e5`/`lon_e5` at 1.1m resolution is far finer than ADS-B position accuracy. `alt_25`
matches the 25-foot quantisation the source already uses. The `-1` ground sentinel keeps the
column integer-typed; readers must translate it back.

### Storage Encoding and Compression

Two entirely separate compressions apply to this pipeline. Conflating them causes bad
decisions, so they are specified separately.

#### Transport (fetch time) - automatic, but verify

readsb stores trace files gzipped on disk and the server returns
**`Content-Encoding: gzip` unconditionally** — including when the client explicitly requests
`Accept-Encoding: identity`. Measured 21,028 wire bytes for a 122,093-byte document, a 5.8x
saving that is free and cannot be turned off.

Node's `fetch` (undici) decompresses transparently; a bare `await res.json()` was verified to
work and return the parsed trace. **A raw `node:http` client, or any library configured with
decompression disabled, will receive gzip bytes and fail to parse JSON.** Phase 7 must assert
this in a test rather than assume it, because the failure mode is a confusing parse error
rather than an obvious transport error.

#### At rest - delta-varint, not zlib

The naive row layout was measured against a packed per-session blob. The important result is
that **almost all of the saving comes from delta-varint packing, and zlib is counterproductive
at realistic session sizes**:

| Points/session | Rows (B/pos) | Blob + zlib | Blob, varint only |
| -------------- | ------------ | ----------- | ----------------- |
| 4              | 29.8         | 18.8        | **15.9**          |
| 7 (measured)   | 29.8         | 15.6        | **14.0**          |
| 10             | 29.7         | 14.7        | **13.3**          |
| 20             | 29.7         | 12.9        | **12.8**          |
| 37             | 29.7         | 12.3        | 12.3              |
| 60             | 29.7         | 13.7        | 13.7              |

zlib's per-blob header and framing overhead exceeds what it recovers below roughly 20 points
per session. The trace study currently measures ~7 DP-thinned points per session, squarely in
the region where **adding zlib makes the database larger**. Any future compression work must
be re-measured at the real session-size distribution, not assumed to help.

#### Decision

**Ship the row layout (29.7 B/position). Do not implement blob packing in v4.3.**

Reasons, in order of weight:

1. The large win was already taken. Scaled integers plus `WITHOUT ROWID` moved the design
   from 86.5 to 29.7 B/position (2.9x). Blob packing is a further ~2x on an already small
   number: roughly 44 MB/year becomes ~21 MB/year at the projected rate. For context,
   `timeseries_stats` alone is ~63 MB steady-state.
2. Rows suit the write pattern. The periodic refresh trigger upserts points into a live
   session repeatedly. A blob would force decompress-append-re-encode on every refresh,
   replacing an indexed upsert with a read-modify-write of the whole session.
3. Rows stay queryable, debuggable with `sqlite3`, and prunable by ordinary `DELETE`.

**If growth exceeds projections**, the escape hatch is compaction rather than a format
change: keep live sessions as rows, and pack a session into a single delta-varint blob when
it is finalized (`trace_state = 'final'`). Live sessions are a handful of aircraft, so
steady-state cost converges on the blob figure while the write path keeps using rows. This
mirrors the time-series compaction already used in this codebase — see
`agent-docs/MEMORY_OPTIMIZATION.md`. Treat it as a follow-up, not v4.3 scope.

### Projected Growth

At ~250 ACARS-active aircraft/day with trace-sourced, DP-thinned positions (~10
points/session at 29.7 B):

| Scenario                                        | rows/day | MB/day | MB/30d | MB/year |
| ----------------------------------------------- | -------- | ------ | ------ | ------- |
| ACARS-gated + DP@100m (adopted)                 | 2,500    | 0.12   | 3.6    | 44      |
| ACARS-gated + DP@100m, busy site (800 aircraft) | 8,000    | 0.38   | 11.5   | 140     |
| ACARS-gated, raw trace (no thinning)            | 9,250    | 0.44   | 13.3   | 162     |
| Original v4.2 design (all aircraft, polled)     | 21,000   | 1.01   | 30.2   | 368     |

For scale: `timeseries_stats` already sits at roughly 63 MB steady-state under its 1,095-day
default retention. The adopted design is a fraction of an existing accepted cost.

### Retention Feature Flag

`ENABLE_POSITION_HISTORY`, default **on**, parsed with the existing `isEnabled()` helper
(`config.ts:151`) and surfaced through `features_enabled` like `ENABLE_ADSB`.

Because positions are fetched on demand rather than accumulated, the flag does **not** gate
availability - only persistence. With the flag off:

- Active sessions still get full trails, served from the in-memory warm cache
- Trails survive in cache for a cooldown period after the session ends
- Nothing is written to `aircraft_positions`; the table stays empty
- Historical drill-down from search returns no trail for ended sessions

That is a materially better flag-off story than the original polling design could offer:
degraded to "no history for departed aircraft", not "no trails at all".

**The flag must not gate the migration.** There is no precedent for config-conditional
migrations in this codebase - `MigrationStep.upgrade` receives only a `Database` handle
(`db/migrations/types.ts:7-11`), no migration reads `process.env`, and `runMigrations()`
throws unrecoverably on an unrecognised schema state (`db/migrate.ts:256-261`). A flag flip
after the migration ran would produce exactly that state. Create the table unconditionally;
gate the **writes**. This matches how `DB_SAVE_DAYS` and `TIMESERIES_RETENTION_DAYS` already
work.

The flag is specced from the start on the understanding that it may be removed if measured
cost stays negligible. Keep it cheap: a single write-path guard plus a prune-path guard.

## New Database Tables (Migrations 16 and 17)

The new tables are split across **two** migrations, deliberately:

| Migration | Tables                                                                                          | Phase |
| --------- | ----------------------------------------------------------------------------------------------- | ----- |
| 16        | `aircraft`, `decoder_variant`, `decoded_messages`, `system_config`, `messages.session_id`        | 1     |
| 17        | `aircraft_positions`                                                                            | 8     |

### Why the Split

`aircraft_positions` is the only table whose design is still open. Its shape depends on
measurements from the trace study (see Open Questions) — specifically whether `trace_full`
truncates long flights, and what the real points-per-session distribution is. If those
results push the design toward the per-session blob layout rejected in Position Schema, the
table changes shape.

This codebase's migration chain is linear, append-only, and `runMigrations()` throws
unrecoverably on an unrecognised schema state (`db/migrate.ts:256-261`). There is no
down-migration. Creating a table before its design is settled therefore means either living
with the wrong schema or spending a second migration to correct it.

Nothing in phases 1-6 touches positions, so deferring costs nothing.

### Migration Numbering and Sequencing

Migration 16 is the next free number. Migrations 1-15 exist; **10 is `rebuild_fts`**, not
these tables. Add `migration16.ts` under `db/migrations/`, export
`migration16_v43Tables`, import it in `db/migrations/index.ts`, and append to the
`MIGRATIONS` array with a fresh 12-hex-character revision string. `LATEST_REVISION` is
derived from the array and needs no manual edit.

**Only one migration-adding task may be in flight at a time.** Two branches that each claim
"the next migration" with different revision hashes will merge cleanly at the text level and
produce a broken revision chain that only fails at runtime, on a user's database. The
`MIGRATIONS` array in `db/migrations/index.ts` is a serialization point: land migration work
first, then fan out parallel tasks.

### Migrations Under This Plan Are Mutable Until v4.3 Ships

**Until v4.3 is released, the migrations it introduces may be edited in place.** If a shape
turns out to be wrong, correct the migration itself — do **not** add a follow-up migration to
undo it.

This holds only because no released version has ever applied them, so no user database
contains them. The only cost is that anyone running the `feat/v4.3` branch must discard their
development database when a migration changes underneath them, which is acceptable for a
development branch.

The append-only, no-down-migration discipline described above resumes the moment v4.3 ships.
Two consequences while the window is open:

- Getting a shape slightly wrong is recoverable, so it is not necessary to defer a table
  purely because one detail is unsettled.
- It is still worth measuring first. Editing a migration is cheap; discovering after release
  that a table is mis-shaped is not, and the window closes at the release, not at merge.

### Branch Naming for v4.3 Task Branches

Task branches use `feat/v4.3-phase-N-slug` and PR into `feat/v4.3`.

The hyphen is not cosmetic. Git stores branches as paths under `refs/heads/`, so
`refs/heads/feat/v4.3` (a file) and `refs/heads/feat/v4.3/phase-1-migration-16` (which needs
`feat/v4.3` to be a directory) cannot coexist. Creating the latter fails with
`cannot lock ref ... 'refs/heads/feat/v4.3' exists`. Any nested-slug scheme under a
long-lived branch name hits this.

Never rebase `feat/v4.3` — task branches are based on it. Merge `origin/main` into it when
main moves, and run `just ci` after each integration merge.

### `aircraft` - Flight Session Registry

Each row represents one flight session. Two appearances of the same aircraft are two rows.
This is intentional - see Session Lifecycle below.

```sql
CREATE TABLE aircraft (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    icao_hex       TEXT,                      -- ICAO 24-bit address (uppercase hex, e.g. "ABC123")
    callsign       TEXT,                      -- Flight number / callsign (e.g. "UAL123")
    tail           TEXT,                      -- Registration (e.g. "N12345")
    first_seen     INTEGER NOT NULL,          -- Unix seconds
    last_seen      INTEGER NOT NULL,          -- Unix seconds; updated on every contact
    is_active      INTEGER NOT NULL DEFAULT 1,-- 1 = session alive, 0 = timed out
    session_type   TEXT    NOT NULL DEFAULT 'adsb',
    -- 'adsb' | 'vdlm2' | 'hfdl' | 'adsc' | 'acars_only'
    -- Controls timeout threshold. See Session Timeout Thresholds below.
    pairing_method TEXT,
    -- 'hex' | 'callsign' | 'tail' | 'acars_only' - how the session was first established
    trace_state    TEXT    NOT NULL DEFAULT 'none'
    -- 'none' | 'pending' | 'live' | 'final' | 'unavailable' - see Trace Fetch Lifecycle
);

CREATE INDEX ix_aircraft_active_hex ON aircraft(is_active, icao_hex);
```

`AUTOINCREMENT` is deliberate and load-bearing, not boilerplate. A plain `INTEGER PRIMARY KEY`
reuses the rowids of deleted rows, so once Phase 6 prunes sessions a stale
`messages.session_id` could silently re-point at a **different, newer** session — violating
Architecture Invariant 5 (sessions are never retroactively re-assigned). `AUTOINCREMENT` makes
a dangling reference stay dangling instead of becoming a wrong one. It costs one
`sqlite_sequence` row.

#### Exactly One Index, and Why the Second Was Dropped

The original plan specified five single-column indexes, was narrowed to two
(`(is_active, icao_hex)` plus `last_seen`), and is now **one**. Measured on real SQLite files,
VACUUMed and `ANALYZE`d, at three cardinalities with the active set sized off arrival rate
rather than retention depth:

| rows (active) | no index | `(is_active, icao_hex)` | gain |
| ------------- | -------- | ----------------------- | ---- |
| 1,750 (36) | 0.0290 ms | 0.0074 ms | 3.9x |
| 5,600 (109) | 0.0885 ms | 0.0074 ms | 12x |
| 91,250 (52) | 1.4249 ms | 0.0080 ms | **178x** |

`EXPLAIN QUERY PLAN` selects it with both columns:
`SEARCH aircraft USING INDEX ix_aircraft_active_hex (is_active=? AND icao_hex=?)`.

**`ix_aircraft_last_seen` was selected by zero of seven candidate queries, at every
cardinality.** With both indexes present, every plan line names `ix_aircraft_active_hex`
instead — including the expiry sweep it was supposedly added for. `is_active = 1` is roughly
0.06% selective and `ANALYZE` knows it, so leading with `is_active` always beats leading with
`last_seen`. It was dead index at 12.79 B/row.

A composite `(is_active, last_seen)` replacement *is* selected for the sweep, but is not
earned either: the sweep costs 1.43 ms at 91,250 rows and runs once every five minutes.

| index set | B/row | index bytes as % of table |
| --------- | ----- | ------------------------- |
| one index (adopted) | 15.80 | 27.5% |
| the plan's two | 28.59 | 49.8% |
| all three identifiers indexed | 62.17 | 108.2% |

Indexing `callsign` and `tail` as well makes the OR-form match query fast
(`MULTI-INDEX OR`), but costs **more in index than the table itself** — the exact mistake
migrations 13 and 15 were written to undo. Rejected.

Cardinality note: `DB_SAVE_DAYS` defaults to 7 but is user-settable, and the shipped
`docker-compose-testing-example.yaml` uses `1000`. `DB_ALERT_SAVE_DAYS` defaults to 120 and
protects alert-matched messages from pruning. The high-cardinality column above is therefore a
real configuration, not a stress test.

Verify with `EXPLAIN QUERY PLAN` before adding any second index.

### Session Identifier Type

The original plan used a `session_id TEXT` UUID as the FK target. **This is rejected.**
Migration 14 removed UUIDs from this schema for measured size reasons (~838 MB projected at
11M rows). Re-introducing a 36-character text key as an FK target would undo that work.

Sessions use the integer `aircraft.id`. Consequently:

- `messages.aircraft_id` (`text(36)`, nullable, dead, never written) is **not** reused.
  Migration 16 adds `messages.session_id INTEGER` alongside it and leaves the dead column
  for a later cleanup migration to drop, keeping migration 16 free of a table rebuild.
- The index question raised by `DB_OPTIMIZATION.md` is resolved: `ix_messages_aircraft_id`
  stays dropped forever. Phase 6 creates `ix_messages_session_id` on the new integer column
  once it is actually populated.

The new column **does** carry a foreign key:

```sql
ALTER TABLE messages ADD COLUMN session_id INTEGER REFERENCES aircraft(id);
```

Verified against SQLite 3.53.4: this is accepted with no table rebuild (legal because the
column is nullable and defaults to NULL), and defaults to `NO ACTION`, so a `DELETE` from
`aircraft` that would orphan a message fails loudly. Deleting a *message* is never obstructed.

`ON DELETE` is deliberately absent. `SET NULL` would let a buggy session prune silently discard
message linkage, and the symptom — a history endpoint quietly returning an empty trail for a
message that genuinely had one — is the plausible-looking kind of wrong this plan keeps warning
about. **`ON DELETE CASCADE` must never appear on this column**: it would delete *messages* when
a session is pruned.

What the FK buys is narrow but real: it converts Phase 6's "only delete sessions with no
surviving messages" from an application promise into a database guarantee. Note that
`AUTOINCREMENT` on `aircraft.id` already prevents the worse failure (a reused rowid making a
stale `session_id` point at a *different* session), so the FK is not carrying that load.

Two operational notes. SQLite enforces a parent `DELETE` by scanning the child table, so
`ix_messages_session_id` must exist before anything deletes from `aircraft`; Phase 6 creates it
and is also the first phase to write the table, so the ordering is satisfied within one phase.
And the failure mode under `NO ACTION` is bounded: `pruneDatabase()` deletes from `messages`
first, so message pruning — the part that actually controls database size — completes before any
session prune can fail.

### `decoded_messages` - Decoded Text Storage

Stores decoder output per message, along with which decoder produced it, so re-processing can
find decodes made by a superseded version. See Decoder Re-processing below.

Every figure in this section is measured against a production database
(`messages_current.db`, 1.47 GB, 3,362,232 messages) using the real installed decoder
(`@airframes/acars-decoder` 1.9.1), not a synthetic payload. **This table was the single
largest storage risk in v4.3** and the plan as originally written would have made it larger
than everything else in the release combined.

#### Corpus Facts That Drive the Design

| Fact | Value |
| ---- | ----- |
| Total messages | 3,362,232 |
| Messages with non-empty `msg_text` | 1,286,979 (38.3%) |
| Messages with no text at all | 2,075,253 (61.7%) |
| Of text-bearing: decode to `full` | 21.7% |
| Of text-bearing: decode to `partial` | 17.7% |
| Of text-bearing: do not decode | 60.5% |
| Text-bearing messages producing any output | 39.5% |
| Distinct `(decoder_name, decoder_version)` pairs | 42 |

So only **15.1% of all messages produce any decoded output at all**. Any design that puts a
row on every message spends most of its bytes on placeholders.

#### The Payload: What to Store

`enrichment.ts:186-204` already reduces the decoder's `DecodeResult` to a small `DecodedText`
before anything reaches the wire. The fields it discards — `raw` (~50 keys including nested
route and wind arrays), `message` (an echo of the input, duplicating `messages.label` and
`messages.msg_text`), `error`, and `decoder.type` — are read **nowhere** in the backend or
frontend. "Store the decoder's output verbatim" was therefore never a real option; it would
persist a large object the product does not consume.

The frontend renders exactly three things: `decoder.decodeLevel`, and `formatted[].label` /
`formatted[].value` (`MessageCard.tsx:397-417`, `decoderUtils.ts:32-57,283-293`).
`decoder.name` is carried but never rendered — it is kept here for re-processing and
diagnostics, not for the UI.

Mean `decoded_json` length over rows that actually decode:

| Encoding | Mean bytes |
| -------- | ---------- |
| Full `DecodeResult` (the strawman) | 915.6 |
| `DecodedText` as built today | 412.2 |
| `formatted` only, `{label, value}` objects | 344.8 |
| `formatted` only, 2-tuples | **239.2** |

The last step is free: `[["Description","..."],["Altitude","35000 ft"]]` carries the same
information as `[{"label":"Description","value":"..."}]` without repeating the keys
`"label"` and `"value"` on every item, which is a 42% cut against `DecodedText`. Because
`decode_level` and the decoder identity are columns, keeping them inside `decoded_json` too
would be pure duplication.

#### Measured Shapes

On-disk bytes, real corpus, VACUUMed, projected to 11M messages with a row on every message:

| Shape | MB at 11M | vs baseline |
| ----- | --------- | ----------- |
| Plan as written, `decoded_json` = full `DecodeResult` | 2,933 | baseline |
| Plan as written, `decoded_json` = `DecodedText` | 1,030 | -65% |
| `formatted` objects | 904 | -69% |
| `formatted` 2-tuples | 717 | -76% |
| \+ variant lookup table | 640 | -78% |
| \+ drop `decoded_at` | 586 | -80% |
| \+ `decode_level` as INTEGER (**adopted**) | 542 | -82% |
| \+ fold level into the variant key (rejected) | 530 | -82% |

Folding `decode_level` into the variant key saves a further 12 MB (2%) but makes a per-message
outcome part of a decoder-identity row and turns every level-filtered query into a join. Not
worth it for 2%.

`decoded_at` was dropped because nothing consumes it: the reprocessor keys on version, and
sweep progress is tracked by `system_config.acars_decoder_reprocess_cursor`. It cost 54 MB at
11M messages for record-keeping alone.

#### Adopted Schema

```sql
CREATE TABLE decoder_variant (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    decoder_name    TEXT,               -- NULL when the message did not decode
    decoder_version TEXT NOT NULL,
    UNIQUE(decoder_name, decoder_version)
);

CREATE TABLE decoded_messages (
    message_id   INTEGER PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
    variant_id   INTEGER NOT NULL REFERENCES decoder_variant(id),
    decode_level INTEGER NOT NULL CHECK(decode_level IN (0, 1, 2)),
    decoded_json TEXT    -- NULL when decode_level = 0; otherwise a JSON array
                         -- of [label, value] 2-tuples, rehydrated to
                         -- DecodedTextItem[] on read
) WITHOUT ROWID;
```

`decode_level` is `0 = none`, `1 = partial`, `2 = full`. The integer encoding saves 44 MB at
11M messages over the `TEXT` form and follows the precedent already set by `aircraft_positions`
(`alt_25`, and its `-1` ground sentinel): integers with a documented mapping and a `CHECK`
constraint, not human-readable strings on every row.

The 42 observed `(decoder_name, decoder_version)` pairs occupy a **single 4 KB page**. Interning
them removes ~19 B/row of repeated text from a table that is 1:1 with `messages`. Its `UNIQUE`
constraint is the lookup path for upsert-on-insert; there is no separate index beside it, so no
duplicate B-tree.

Keyed on `messages.id`, not a UUID, for the same reason as sessions. The relationship is 1:1,
so `message_id` is the primary key directly. Under `WITHOUT ROWID` that primary key **is** the
table, which also means the `ON DELETE CASCADE` from `messages` needs no extra index.

#### Row Policy: Text-Bearing Messages Only

**Do not create a row for a message with empty `msg_text`.** No decoder version can ever decode
a message with no text, so such a row would be a permanent placeholder that can never change.
This saves 78 MB at 11M messages and makes the reprocessor's first pass meaningful:

| State | Meaning |
| ----- | ------- |
| No row, `msg_text` empty | Nothing to decode, ever. Not a re-processing candidate. |
| No row, `msg_text` non-empty | Never processed. This is re-processing pass 1. |
| Row present | Processed; `variant_id` says by which decoder and version. |

This supersedes the original note that `decode_level = 'none'` rows exist to distinguish "never
tried" from "tried and failed". That distinction is preserved — but only where it means
something, which is text-bearing messages.

With this policy the adopted shape costs **142 MB on the 3.36M-message production corpus** and
roughly **464 MB at 11M messages**, against 896 MB and 2,933 MB respectively for the plan as
originally written.

#### No `ix_decoded_version_level`

**Do not create it.** Measured at 1M rows it costs 19.66 B/row — **206 MB at 11M messages** —
and buys nothing:

| Query | Without index | With index |
| ----- | ------------- | ---------- |
| `WHERE decoder_version != ?` (as the plan describes the sweep) | 0.0262 ms `SCAN` | 0.0236 ms `SCAN USING COVERING INDEX` |
| `WHERE decoder_version = ? AND decode_level = ?` | 0.0375 ms | 0.0343 ms |
| Cursor sweep `WHERE message_id > ? ORDER BY message_id` | 0.0459 ms | 0.0470 ms, uses `PRIMARY KEY` |
| Single-message retrieval JOIN | 0.0016 ms | 0.0023 ms, uses `PRIMARY KEY` |

Three reasons it cannot pay: `!=` is not sargable so no seek is possible; after a version bump
essentially every row matches, so a scan is already optimal; and the index is not selective —
one installed version times three levels is **three distinct keys** over millions of rows. Both
paths that matter (the cursor sweep and single-message retrieval) go via the primary key, which
under `WITHOUT ROWID` is the table.

The one shape that gains is ordering by decode-level priority (40.7 ms versus 71.1 ms), and
both variants build a `TEMP B-TREE` at ~40 ms per 250-row batch, so Phase 4 must not use that
shape regardless — it should run priority passes as separate cursor sweeps. Unlike a foreign
key, `CREATE INDEX` needs no table rebuild, so this can be added later with evidence at no
cost.

**Growth note**: this table is 1:1 with `messages` and inherits its retention bound via
`ON DELETE CASCADE`. At ~10% of database size it sits right on the Storage Discipline trigger
threshold, which is why Open Question 7 exists.

## Session Lifecycle

### Session Types and Timeout Thresholds

A session is considered the "same flight" as long as a contact arrives within the timeout
window. After the timeout, any new contact creates a new session row, even if `icao_hex`,
`callsign`, and `tail` are identical.

| `session_type` | Timeout    | Rationale                                                |
| -------------- | ---------- | -------------------------------------------------------- |
| `adsb`         | 20 minutes | Local Mode S; aircraft lands or leaves range quickly     |
| `vdlm2`        | 45 minutes | Slightly longer range; taxi and gate messages common     |
| `hfdl`         | 6 hours    | Oceanic; multi-hour gaps between position reports normal |
| `adsc`         | 12 hours   | Polar/oceanic; very long gaps by design                  |
| `acars_only`   | 90 minutes | No position data; conservative to avoid false splits     |

The `session_type` is set to the most authoritative source that has contributed to the session.
Priority: `adsb` > `vdlm2` > `hfdl` > `adsc` > `acars_only`. If an `acars_only` session
later receives ADS-B data, `session_type` is upgraded and `pairing_method` is updated.

**These timeouts govern session identity only. They must not be used as trace-fetch
deadlines** - see Trace Fetch Lifecycle. Trace availability is a property of readsb, not of
this application's session model, and the `hfdl` (6h) and `adsc` (12h) windows are far beyond
any observed trace lifetime.

### Session Matching Algorithm

On every inbound message or ADS-B position, the session service runs:

```text
1. Query active sessions (is_active = 1) matching any of: icao_hex, callsign, tail
2. For each candidate, compute elapsed = now - last_seen
3. If elapsed < TIMEOUT[session_type]:
     -> Update last_seen, enrich identifiers if new data, return session id
4. If no live match:
     -> Create new session, set session_type from message source
     -> Return new session id
```

Matching priority is `icao_hex` > `callsign` > `tail`. If a session is found by callsign
but the incoming data includes a new `icao_hex` not yet on that session, update the session
row with the hex. This is "session enrichment" - identifiers accumulate over a session's life.

**Step 1 must be issued as separate probes in priority order, not as one three-way `OR`.**
This is measured, and the sole justification for `ix_aircraft_active_hex` depends on it. With
`WHERE is_active = 1 AND (icao_hex = ? OR callsign = ? OR tail = ?)` the planner can only use
the index's **leading column** — it degrades to `SEARCH ... (is_active=?)`, an index scan of
the whole active set with the identifiers filtered in place. Probing
`WHERE is_active = 1 AND icao_hex = ?` first gets the full two-column seek
(`is_active=? AND icao_hex=?`), 0.0080 ms versus 1.4249 ms unindexed at 91,250 rows. Fall
through to the callsign probe, then the tail probe, only when the previous one misses; those
two are served by the leading-column restriction and need no index of their own.

### Session Expiry

A background task (extending the existing scheduler in `services/background-services.ts`)
runs every 5 minutes and marks sessions inactive:

```sql
UPDATE aircraft SET is_active = 0
WHERE is_active = 1
  AND last_seen < (? - CASE session_type
        WHEN 'adsb'  THEN 1200  WHEN 'vdlm2' THEN 2700
        WHEN 'hfdl'  THEN 21600 WHEN 'adsc'  THEN 43200
        ELSE 5400 END)
```

**Use the single `CASE` statement, not one statement per `session_type`.** Measured, and it
inverts the intuitive answer: the per-type form is sargable and the `CASE` form is not, yet
`CASE` wins because five statements each traverse the active set while one traverses it once.
At 91,250 rows with no index: 1.43 ms for `CASE` versus 7.24 ms for five per-type statements.
The same direction holds in every index configuration tested. Sargability does not pay once
the leading-column restriction has already narrowed the scan to a few dozen rows.

Inactive sessions are retained in the database for historical queries. They are never deleted
by the expiry process.

**Retention**: sessions and their positions are pruned by the existing `pruneDatabase()`
schedule, not by expiry. A session whose messages have all aged out of the 7-day window has
no reason to persist. This must be added to `prune.ts` in Phase 6 - a session table that
grows forever would defeat the point of this document.

### Callsign Reuse Edge Case

Airlines reuse flight numbers daily. `UAL123` on Monday is a different aircraft than `UAL123`
on Tuesday. The timeout logic handles routine cases, but a defensive check applies when:

- A session exists with a matching callsign
- Elapsed time is > 80% of the session's timeout threshold
- The session has no `icao_hex` (callsign-only match)

In this case, treat the incoming contact as a new session. Log a warning. This avoids
erroneously extending a stale callsign-only session.

## Trace Fetch Lifecycle

Three mechanisms, all driven by `services/trace-fetcher.ts`. Each is independently testable
and each has a distinct trigger.

`aircraft.trace_state` tracks progress: `none` -> `pending` -> `live` -> `final`, or
`unavailable` when readsb has no trace for the hex.

### Preconditions

- `/data/receiver.json` reports `haveTraces: true`, checked once at startup and cached. If
  false, the whole subsystem is inert and `trace_state` stays `none`.
- The session has a known `icao_hex`. Traces are keyed on hex only; a callsign-only or
  tail-only session cannot be fetched for until enrichment supplies a hex.
- A 404 is a **normal outcome**, not an error. Satellite-only aircraft (`adsc`) will 404
  almost always. Log at debug, set `trace_state = 'unavailable'`, do not retry aggressively.

### Trigger 1 - On First ACARS Pairing

When a session first acquires an ACARS message and has a hex, fetch `trace_full` immediately.
This is the high-value path: it retrieves position history from *before* the message arrived,
at no storage cost for aircraft that never send one.

### Trigger 2 - Periodic Refresh of Active Sessions

A scheduler task refreshes traces for active, ACARS-paired sessions.

- Interval: **60 seconds** minimum. readsb rewrites trace files every
  `json_trace_interval` (15s), so polling faster is pure waste.
- Use `If-Modified-Since` (or `If-None-Match`) from the stored validator. Unchanged files
  cost a 304 and near-zero bytes.
- **Batch with a concurrency cap of 4-8.** Measured throughput is ~1 ms/request against a
  local readsb, but a remote or shared tar1090 deserves politeness. Do not fan out to all
  sessions at once.
- Only ACARS-paired sessions are refreshed. This is typically 5-20 aircraft, not 150.
- Refreshed points are clipped by the Trace-to-Session Attribution Rule and upserted on
  `(session_id, timestamp)`, so overlap between `full` and `recent` is idempotent. Observed
  overlap is 100-270s.

### Trigger 3 - Finalizer on Dropout

The finalizer captures the definitive trace once an aircraft stops being seen.

**Trigger on dropout detection, not session expiry.** An aircraft is considered dropped when
absent from `aircraft.json` for two consecutive poll cycles. Session expiry is a fallback in
case dropout was missed.

The deadline is independent of `session_type`:

- Capture within **10 minutes** of last contact. Trace persistence was verified at 30+ minutes
  but the upper bound is unknown, so the deadline is deliberately conservative.
- Never derive the deadline from the session timeout table. A 12-hour `adsc` timeout would
  guarantee a 404.

On success: apply the attribution rule, thin, store, set `trace_state = 'final'`. A finalized
session is never refreshed again.

### Returning Aircraft

If an aircraft returns and matches an existing active session, refresh resumes and the newly
fetched trace supplies the coverage gap plus the earlier positions. Upsert on
`(session_id, timestamp)` makes re-ingesting the overlapping portion a no-op.

If it returns *after* the session expired, it is a new session by definition. The new session
fetches its own trace and clips it to its own `first_seen`, so the previous flight's positions
are discarded by step 2 of the attribution rule even if readsb still has them.

### Warm Cache

Trace points for active sessions are held in memory alongside the existing message ring
buffer (`services/message-ring-buffer.ts`), so the frontend never waits on a DB read for a
live aircraft's trail. This cache is what makes `ENABLE_POSITION_HISTORY=false` tolerable:
active sessions keep full functionality, plus a cooldown window after the session ends.

## Retroactive Pairing

When a new ADS-B target appears, the backend checks for historical ACARS messages that
should belong to this session but arrived before the ADS-B signal was first received.

```text
1. New ADS-B contact creates or updates a session (session id S, hex H, callsign C, tail T)
2. Query: SELECT id FROM messages
          WHERE session_id IS NULL
            AND msg_time > (first_seen - LOOKBACK_WINDOW)
            AND (icao = H OR flight = C OR tail = T)
3. For each match: UPDATE messages SET session_id = S WHERE id = ?
4. Emit session_paired event with [session id, [ids]]
```

`LOOKBACK_WINDOW` is 60 minutes for `adsb` sessions. For `hfdl`/`adsc` sessions the window
scales with the session timeout.

Retroactive pairing is also run on session enrichment - when a new identifier (e.g. `icao_hex`)
is added to an existing session, the query runs again with the newly available identifier.

**Query cost warning**: this query has no supporting index. `messages` has only
`ix_messages_icao`, `ix_messages_msgno`, and `ix_messages_type_time` after migration 15;
`flight` and `tail` indexes were deliberately dropped. Run `EXPLAIN QUERY PLAN` during
implementation. If it degrades, prefer narrowing the time window over adding indexes back -
those indexes were removed for measured size reasons and cost ~154 MB at 11M rows.

## Decoded Message Storage and Re-processing

### At Ingest Time

When a new ACARS message arrives and is stored, the backend:

1. Calls `@airframes/acars-decoder` with the message text and label
2. Writes one row to `decoded_messages` (with `decode_level = 'none'` if undecoded)
3. Sets `decoded_at` and `decoder_version` from the installed package version
4. The `decodedText` field on the outbound socket message is populated from this row

The `enrichMessage()` function in `formatters/enrichment.ts` is the correct integration point.
It already calls the decoder inline (`enrichment.ts:176`) but **does not persist the result** -
every retrieval path re-decodes. Post-v4.3 it writes to `decoded_messages` and subsequent
retrievals JOIN rather than re-decode.

The paths that currently re-decode, and therefore benefit:

| Path                    | Location                          | Cost                          |
| ----------------------- | --------------------------------- | ----------------------------- |
| Live ingest             | `background-services.ts:352`      | 1 per message (unavoidable)   |
| Ring buffer warm-up     | `message-ring-buffer.ts:348,375`  | up to 700 decodes at startup  |
| Search results          | `socket/handlers/search.ts:88`    | every query                   |
| Alert term search       | `socket/handlers/alerts.ts:292`   | every query                   |
| Alerts by term          | `socket/handlers/alerts.ts:337`   | every query                   |

### Version Detection at Startup

```typescript
// At startup, after DB is initialized
const installed = getInstalledDecoderVersion(); // from @airframes/acars-decoder/package.json
const stored = systemConfig.get("acars_decoder_installed_version");

if (installed !== stored) {
  logger.info("acars-decoder version change detected", { stored, installed });
  systemConfig.set("acars_decoder_installed_version", installed);
  decoderReprocessor.schedule();
}
```

A simple string equality check is sufficient. Semantic versioning comparison is unnecessary -
any version change (including a downgrade) warrants re-processing to ensure consistency.

### Background Reprocessor

The reprocessor is a low-priority background service added to the scheduler. It must not
starve the event loop while 100k+ messages are being re-processed.

**Processing order** (most likely to benefit from a new decoder version first):

1. Messages with no row in `decoded_messages` (legacy data, never processed)
2. Messages where `decode_level = 'none'` and `decoder_version != installed`
3. Messages where `decode_level = 'partial'` and `decoder_version != installed`
4. Messages where `decode_level = 'full'` and `decoder_version != installed`

**Execution model**:

- Batch size: 250 messages per iteration
- Yield between batches: `await new Promise(resolve => setImmediate(resolve))`
- Persist cursor to `system_config.acars_decoder_reprocess_cursor` after each batch
- On restart, read cursor and resume from that `messages.id`
- On completion, set `acars_decoder_reprocess_status = 'completed'`

**When a decode changes**:

If re-processing produces a different `decode_level` or `decoded_json` from what is stored,
the reprocessor updates the row and emits a `message_decode_updated` Socket.IO event:

```typescript
// Server -> client
socket.emit("message_decode_updated", {
  id: number;
  decodedText: DecodedText | null;
});
```

Clients update any matching message currently in their view. This lets users watching Live
Messages see decodes improve in real time as the reprocessor runs.

## Backend Processing Pipeline Changes

### What Moves from Frontend to Backend

| Concern                                  | Current location                          | v4.3 location                                   |
| ---------------------------------------- | ----------------------------------------- | ----------------------------------------------- |
| `@airframes/acars-decoder` text decoding | Backend (`enrichment.ts:176`) - done      | Backend (now persisted to DB)                   |
| Alert term matching                      | Backend (`insert.ts:244-399`) - done      | Unchanged                                       |
| Duplicate detection (3 strategies)       | Frontend (`messagesSlice.ts:280-462`)     | Backend (at ingest, before DB write)            |
| Multi-part merging (AzzA, AAAz)          | Frontend (`messageDecoder.ts:125-321`)    | Backend (accumulate parts, write merged)        |
| Message grouping by identifier           | Frontend (`messagesSlice.ts:208-278`)     | Backend (replaced by session service)           |
| ADS-B / ACARS pairing                    | Frontend (3 separate implementations)     | Backend (session service + retroactive pairing) |
| Culling decisions                        | Frontend (`messageCulling.ts:108-167`)    | Backend (controls what is sent per client)      |

The frontend becomes a **render target**: it receives pre-processed, pre-grouped,
pre-decoded data and renders it. It performs no business logic on messages.

Note the three independent ADS-B pairing implementations that Phase 10 must collapse:
`utils/aircraftPairing.ts:128-162`, `utils/messageCulling.ts:32-91`, and
`components/MessageGroup.tsx:89-111`.

### New Ingest Pipeline

```text
TCP message arrives
  -> MessageQueue.push()
  -> Dedup check (3 strategies, against recent messages)
      -> Duplicate: increment counter, do not insert new row
      -> Multi-part: accumulate in memory, merge when complete, then continue
  -> DB insert (messages table)
  -> Session matching (find or create aircraft session, set session_id)
  -> enrichMessage() - field normalization, airline lookup, ground station lookup
  -> decoded_messages write (decoder output + version)
  -> Alert term matching -> alert_matches write if matched
  -> Trace fetch trigger if first pairing for this session
  -> Broadcast session_messages_updated to all clients
```

Dedup at ingest is a **behaviour change with a data consequence**: duplicate receptions are
currently each persisted as a separate `messages` row. Suppressing them reduces DB growth,
but the "duplicates" counter the frontend currently derives must be persisted instead, or
that information is lost. Decide explicitly in Phase 8.

## Frontend Changes

### What the Frontend No Longer Does

- No message grouping logic (`messagesSlice.ts:208-278` gutted)
- No duplicate detection (`messagesSlice.ts:280-462`, `services/messageDecoder.ts:75-116`)
- No multi-part merging (`services/messageDecoder.ts:125-321`)
- No ADS-B/ACARS pairing (all three implementations removed)
- No culling (`utils/messageCulling.ts` deleted)

The frontend already does no decoding and no alert matching - those are backend-only today.

### New AppStore Shape

```typescript
// Replaces MessageGroup-based structure
interface AppStore {
  sessions: Map<number, AircraftSession>; // keyed by session id
  adsbPositions: Map<string, Aircraft>; // keyed by icao_hex (live map positions)
  filters: LiveFilters;
  connectionState: "connected" | "disconnected" | "reconnecting";
  // ... alerts, terms, status unchanged
}
```

### State-Based Filtering

Filter changes follow this flow:

1. User changes a filter in the UI
2. Frontend emits `set_live_filters` with new filters
3. Frontend clears its sessions map immediately (shows loading state)
4. Backend sends `initial_state` with sessions matching the new filter
5. Frontend populates sessions map from `initial_state`
6. Backend continues sending incremental updates (`session_messages_updated`, etc.)

This eliminates client-side filter logic entirely. The frontend never needs to decide which
messages to show or hide - the backend sends only what matches the current filter.

## Architecture Invariants

These rules must be preserved throughout v4.3 implementation. Rules 1-3 are the storage
constraint from Storage Discipline, restated as hard checks.

1. **Storage cost outranks feature completeness.** A feature that cannot fit a defensible
   storage budget is descoped, gated, or redesigned — not shipped and apologised for.
2. **No index without `EXPLAIN QUERY PLAN` evidence in the PR.** No index may duplicate a
   primary key or another index. Migrations 13 and 15 exist to undo exactly that mistake, at
   a measured cost of ~1,086 MB at 11M rows.
3. **No storage optimisation without before/after byte counts on realistic data.** Intuition
   has been wrong twice already in this plan. Measure first.
4. **The backend is the source of truth.** The frontend renders; it does not compute.
5. **Sessions are immutable once created.** A new flight is always a new row, even for the
   same aircraft. Historical data must not be retroactively re-assigned to different sessions.
6. **Every trace point is clipped to its session before storage.** Never trust a trace file
   to contain exactly one flight leg. See the Trace-to-Session Attribution Rule.
7. **Trace availability is never assumed.** 404 is a normal outcome. `haveTraces: false`,
   satellite-only aircraft, and non-readsb sources must all degrade to no-trail, not error.
8. **Integer keys only.** No UUID or text surrogate keys in new schema. Migration 14 removed
   them for measured size reasons.
9. **Cascade deletes are the only pruning mechanism for `decoded_messages`.** Never delete
   from it directly. Delete from `messages` and let the cascade handle it.
10. **Every new table has a retention story before it ships.** An unbounded table is a bug.
11. **The decoder reprocessor is non-blocking.** It must yield between batches. A slow
    re-process must never delay message ingestion or socket broadcasts.
12. **All new services follow the singleton pattern** used by `MessageQueue`, `AdsbPoller`,
    etc. Export a `getXxx()` factory and a `destroyXxx()` for test cleanup.
13. **Every phase ships with tests.** See `TESTING.md` and the Testing Mandate in `AGENTS.md`.

### Is Persisting Decodes Worth Its Storage?

Measured on the production corpus with the real decoder, weighted over the actual mix of
decode outcomes: **0.00836 ms per decode**. Counter-intuitively the messages that *fail* to
decode are the slowest class (0.0111 ms), so a sample is not biased toward the flattering
answer.

Against that, the re-decode sites the plan cites as justification for persisting:

| Site | Decodes | Cost |
| ---- | ------- | ---- |
| Ring-buffer warm-up at startup | 700 | 5.85 ms |
| Search returning 50 results | 50 | 0.42 ms |
| Search returning 500 results | 500 | 4.18 ms |
| Alert term search, 200 results | 200 | 1.67 ms |

So the performance case for `decoded_messages` is worth roughly **6 ms at startup and 4 ms on
a large search**, in exchange for ~464 MB at 11M messages and ~10% database growth. On its own
that is a poor trade, and Storage Discipline says to surface it rather than absorb it.

The argument cuts deeper than storage. **Decode-on-read is always current by construction.** A
retrieval path that decodes with the installed decoder can never return a stale decode, which
means:

- The staleness that Phase 4 exists to repair is *created* by Phase 3's persistence.
- "A new version of `@airframes/acars-decoder` silently leaves old messages undecoded" — one of
  the stated reasons v4.3 exists — is only true if decodes are persisted. Decode-on-read
  upgrades all history the instant the package is bumped, for free.
- Dropping persistence would remove the reprocessor, its cursor, all three
  `acars_decoder_*` `system_config` keys, and the `message_decode_updated` and
  `decoder_reprocess_progress` events.

Arguments genuinely on the side of persisting, stated fairly:

1. **SQL-queryable decoded text.** FTS over decoded output, or alert matching against decoded
   rather than raw text, requires persistence. Nothing does this today (alert matching runs on
   raw text in `insert.ts:244-399`) and it is not in Additional Features, but retrofitting it
   later would need a backfill.
2. **Regression protection.** If a decoder upgrade makes a decode *worse*, persistence keeps
   the previous good output. Decode-on-read would lose it silently.
3. **Target hardware.** The timings above were taken on a development machine, not on the
   Pi-class hosts adsb.im deploys to. Even assuming 10x slower, startup warm-up is ~58 ms and
   a 500-result search ~42 ms, which is still small — but this has not been measured on the
   real target.

Until this is resolved, `decoded_messages` and `decoder_variant` are specified above as
measured, so that building them is cheap if the answer is "persist" and discarding them costs
only a migration edit if it is not — see Migrations Under This Plan Are Mutable Until v4.3
Ships.
